> **[OPTIONAL - multilingual projects only]** If your project is single-language, skip this rule.

# Internationalization (i18n)

Rules governing translation of user-facing strings across the stack. Covers frontend and backend with a unified key structure and a single source of truth for user locale.

Examples throughout this document use React + a lightweight TypeScript module on the frontend and Laravel on the backend. The **principles** (priority chain, config-driven fallback, JSON translation columns, no-hardcoded-strings) are framework-agnostic - adapt examples to your chosen stack (Django gettext / `django-i18n`, Rails I18n, Next.js `next-intl`, Vue i18n, ASP.NET `IStringLocalizer`, etc.).

---

## Scope

Applies to both codebases:

- **Frontend** - `<project>/frontend/` (or `<web-app>/`)
- **Backend** - `<project>/backend/` (or `<server-app>/`)

Typical deployment: single domain via reverse proxy. Frontend served at `/`, API at `/api/v1/*`.

**Supported locales:** define an explicit whitelist per project, e.g. `['en', 'ru']`, `['en', 'de', 'fr']`. Default and ultimate fallback: one locale from the whitelist, configured centrally.

---

## Frontend: Own Lightweight Solution

`[EXAMPLE - React 19]` Adapt to your frontend framework. The principles (no heavy library, priority chain, missing-key fallback) apply regardless.

The frontend MUST NOT use `react-i18next`, `i18next`, `FormatJS`, `lingui`, `next-intl`, or any other i18n library unless the chosen framework has no reasonable alternative. For React, we ship a homemade module (`~30 lines`) at `frontend/src/lib/i18n.ts` exposing:

- `t(key: string, params?: Record<string, string | number>): string`
- `useTranslation(): { t, locale, setLocale }`
- `setLocale(locale: SupportedLocale): void`

Reasons: zero runtime dependencies, full control over priority chain and fallback behavior, trivial integration with the data-fetching layer (TanStack Query, SWR, etc.) and HTTP client interceptors.

For other frameworks (Flutter intl, Vue i18n, next-intl), prefer the community-standard minimal library and enforce the same rules below.

## File Structure

Identical layout on both sides. Keys and namespaces match 1:1.

```
frontend/src/lang/
├── en/
│   ├── common.json
│   ├── auth.json
│   ├── dashboard.json
│   ├── settings.json
│   ├── <domain>.json        # project-specific feature area(s)
│   ├── validation.json
│   └── errors.json
└── <other-locale>/
    └── ...same namespaces...

backend/lang/                 # [EXAMPLE - Laravel] adapt to your backend framework
├── en/
│   ├── common.php
│   ├── auth.php
│   ├── dashboard.php
│   ├── settings.php
│   ├── <domain>.php
│   ├── validation.php
│   └── errors.php
└── <other-locale>/
    └── ...same namespaces...
```

**Namespaces:** `common`, `auth`, `dashboard`, `settings`, `validation`, `errors`, plus one `<domain>` namespace per major feature area. Add new namespaces only for a whole new feature area, never for a single screen.

## Naming Conventions

- **Dot-notation** keys, camelCase segments: `settings.general.companyName`
- First segment always matches the namespace/file: `auth.login.title` lives in `auth.json` / `auth.php`
- Keys are identical on frontend and backend for any string that may appear on both sides (e.g. `validation.required`, `errors.unauthorized`)
- No spaces, no snake_case, no kebab-case in keys
- Placeholders use curly braces on the frontend: `"greeting": "Hello, {name}!"`
- Backend placeholder syntax follows the framework's convention (Laravel `:name`, Django `%(name)s`, Rails `%{name}`, .NET `{0}` or named)

```json
// frontend/src/lang/en/settings.json
{
  "general": {
    "title": "General settings",
    "companyName": "Company name",
    "saveSuccess": "Settings for {company} saved."
  }
}
```

```php
// [EXAMPLE - Laravel] backend/lang/en/settings.php
return [
    'general' => [
        'title' => 'General settings',
        'companyName' => 'Company name',
        'saveSuccess' => 'Settings for :company saved.',
    ],
];
```

> Each framework keeps its native placeholder syntax. When the same key exists on both sides, author two copies using each side's convention.

## Priority Chain

The chosen locale is resolved deterministically. `user.language` is the single source of truth whenever an authenticated user is in context.

### Frontend

| Priority | Source | Applies when |
|----------|--------|--------------|
| 1 | `user.language` from API (`GET /api/v1/auth/me` or `GET /api/v1/profile`) | User is authenticated |
| 2 | `navigator.language` (or platform equivalent) mapped to supported locales | Guest pages only (login, forgot-password, reset-password, accept-invitation) |
| 3 | Configured default locale | Nothing above resolved |

### Backend

| Priority | Source | Applies when |
|----------|--------|--------------|
| 1 | Framework locale setter from `user.language` via middleware | Request is authenticated |
| 2 | `Accept-Language` header mapped to supported locales | Request is a guest |
| 3 | Configured default locale | Nothing above resolved |

**Forbidden:**

- `localStorage` / `sessionStorage` / cookies caching of locale preference
- Any browser autodetect path for authenticated users
- Hardcoded strings in templates / components / controller responses
- Reading `Accept-Language` for authenticated requests on the backend

---

## Fallback Locale: Config Only

The fallback locale MUST be resolved at runtime from configuration. NEVER hardcode `'en'` (or any other locale string) as a fallback anywhere in the codebase.

- **Backend:** read from the framework's config system (e.g. `config('app.fallback_locale')` in Laravel, `settings.LANGUAGE_CODE` in Django, `I18n.default_locale` in Rails). Never inline a locale string after a `??`, in an intl-helper default, in a `match` default, or anywhere else a fallback decision is made.
- **Frontend:** read from a single exported constant (e.g. `DEFAULT_LOCALE` from `frontend/src/lib/i18n.ts`). Never inline a locale string in component code, accessors, or resolvers.

**Reason:** single source of truth. If the project ever adds a new default language or changes fallback strategy, one config/constant change must suffice - no codebase-wide hunt for hardcoded strings.

### Bad / Good

`[EXAMPLE - Laravel]`

```php
// BAD - hardcoded fallback
return $this->name_translations[$locale] ?? $this->name_translations['en'] ?? $this->code;

// BAD - hardcoded fallback in intl call
$name = Locale::getDisplayRegion('-'.$isoCode, 'en');

// BAD - hardcoded fallback in resource
'language' => $this->language ?? 'en',

// GOOD - fallback read from config
$fallback = config('app.fallback_locale');
return $this->name_translations[$locale] ?? $this->name_translations[$fallback] ?? $this->code;

// GOOD - fallback read from config at the call site
$fallback = (string) config('app.fallback_locale');
$name = Locale::getDisplayRegion('-'.$isoCode, $fallback);
```

```ts
// BAD - hardcoded literal fallback
const locale = user?.language ?? 'en';

// GOOD - fallback via exported constant
import { DEFAULT_LOCALE } from '@/lib/i18n';
const locale = user?.language ?? DEFAULT_LOCALE;
```

### Where this rule applies

- Model accessors / resolvers for any `name_translations`-style JSON column
- Resolver helpers, service methods, controllers, API Resources / DTOs
- Factories, seeders, fixtures, and their default values for `language` columns
- Test expectations asserting fallback behavior (assert against the config value, not a literal)
- Intl helpers: display-region/language/name calls, any "display locale" second argument
- Middleware defaults when a config miss is possible (use the config key itself, not a repeated literal)

### Allowed exceptions

These are NOT fallbacks and are allowed to contain literal locale strings:

- **Dictionary / seed data:** `['en' => 'US Dollar', 'ru' => 'Доллар США']` - these are keyed translations, not fallbacks
- **The central config file itself:** one authorized hardcoded location that feeds the env default
- **HTML `<html lang="en">` in locale-specific email templates:** locale-specific templates may hardcode their own language attribute
- **Test helpers that explicitly set a known locale to isolate a test** - this is test setup, not a production fallback

If you are unsure whether a literal locale string counts as a fallback: ask "would this need to change if we switched the default language?" If yes, it's a fallback and must come from config.

## Frontend API

`[EXAMPLE - React 19]`

```ts
// frontend/src/lib/i18n.ts (public surface only)
export type SupportedLocale = 'en' | 'ru';

export function setLocale(locale: SupportedLocale): void;
export function t(key: string, params?: Record<string, string | number>): string;
export function useTranslation(): {
  t: typeof t;
  locale: SupportedLocale;
  setLocale: typeof setLocale;
};
```

### Usage in components

```tsx
import { useTranslation } from '@/lib/i18n';

export function SettingsHeader({ companyName }: { companyName: string }) {
  const { t } = useTranslation();

  return (
    <header>
      <h1>{t('settings.general.title')}</h1>
      <p>{t('settings.general.saveSuccess', { company: companyName })}</p>
    </header>
  );
}
```

### HTTP client interceptor

Every outbound request carries the current locale so the backend can honor it on guest endpoints. For authenticated endpoints the backend ignores the header and trusts `user.language`, but we send it anyway for consistency.

```ts
// [EXAMPLE - Axios]
import axios from 'axios';
import { getLocale } from '@/lib/i18n';

export const api = axios.create({ baseURL: '/api/v1' });

api.interceptors.request.use((config) => {
  config.headers = config.headers ?? {};
  config.headers['Accept-Language'] = getLocale();
  return config;
});
```

### Missing-key fallback

1. Look up key in the active locale bundle
2. If missing, look up in the default locale bundle
3. If still missing, return the key itself verbatim (e.g. `settings.general.companyName`) so regressions are visible in the UI and caught in review

## Backend API

`[EXAMPLE - Laravel]` Adapt to your backend framework - the principle is the same: always route user-facing strings through the translation helper, never hardcode.

Standard Laravel helpers. No custom wrappers.

```php
// Simple translation
$title = __('settings.general.title');

// With parameters
$message = __('settings.general.saveSuccess', ['company' => $team->name]);

// Inside Blade (if ever used)
{{ __('dashboard.welcome', ['name' => $user->name]) }}
```

Equivalents in other frameworks: Django `gettext('settings.general.title')`, Rails `I18n.t('settings.general.title')`, Next.js `t('settings.general.title')` via `next-intl`, .NET `_localizer["settings.general.title"]`.

### Setting locale from authenticated user

`[EXAMPLE - Laravel middleware]`

```php
public function handle(Request $request, Closure $next): Response
{
    if ($user = $request->user()) {
        app()->setLocale($user->language);
    } else {
        $header = $request->header('Accept-Language');
        app()->setLocale($this->resolveFromHeader($header));
    }

    return $next($request);
}
```

### Validation messages

Always return messages through the translation helper. Never hardcode strings in validator message maps.

`[EXAMPLE - Laravel FormRequest]`

```php
public function messages(): array
{
    return [
        'name.required' => __('validation.required', ['attribute' => __('settings.general.companyName')]),
        'email.email'   => __('validation.email'),
    ];
}
```

### Missing-key fallback

Most frameworks fall back to the key itself when a translation is missing. Ensure the configured fallback locale is fully translated so the chain `target → fallback → key` is preserved.

## Reference Data Pattern

Reference tables with genuinely translatable names (countries, currencies, languages, categories) carry a `name_translations` JSON column. No separate `translations` table.

> **Brand names are NOT localized.** Partners, affiliate networks, advertisers and similar brand-name entities use a plain `name` VARCHAR column. The JSON pattern is only for reference data that has natural translations.

Reference tables carry BOTH a plain `name` VARCHAR column (English default, denormalized cache for fast non-localized queries, joins, sorting, imports) AND a `name_translations` JSON column (source of truth for localization). The `name` column is written at seed time with the English value; a `localized_name`-style accessor picks the locale-appropriate string from JSON with fallback to the column.

### Schema

`[EXAMPLE - Laravel migration]`

```php
Schema::create('countries', function (Blueprint $table) {
    $table->id();
    $table->string('code', 2)->unique();
    $table->string('name'); // English name, cached denormalized copy for fast queries
    $table->json('name_translations'); // {"en": "Ukraine", "ru": "Украина"}
    $table->timestamps();
});
```

### Model

`[EXAMPLE - Laravel Eloquent]`

```php
protected $fillable = ['code', 'name', 'name_translations'];

protected function casts(): array
{
    return [
        'name_translations' => 'array',
    ];
}

public function getLocalizedNameAttribute(): string
{
    $translations = $this->name_translations ?? [];
    $locale = app()->getLocale();
    $fallback = (string) config('app.fallback_locale');

    return $translations[$locale]
        ?? $translations[$fallback]
        ?? $this->name
        ?? $this->code;
}
```

### API Resource

`[EXAMPLE - Laravel API Resource]`

```php
class CountryResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id'   => $this->id,
            'code' => $this->code,
            'name' => $this->localized_name, // returns locale-aware string
        ];
    }
}
```

### Example response

```json
{
  "data": {
    "id": 42,
    "code": "UA",
    "name": "Украина"
  }
}
```

The frontend receives a ready-to-render string. It does not pick a locale out of `name_translations` itself.

## Language Switching (UX Flow)

Triggered from Settings → Profile.

1. User selects a new language from a `<Select>`
2. Frontend calls `PATCH /api/v1/profile` with `{ "language": "ru" }`
3. Backend validates against supported locales, updates `users.language`, returns fresh user DTO
4. Frontend calls `setLocale('ru')` on success → active locale bundle is swapped → components re-render
5. **No page reload.** The data-fetching layer refetches any queries whose responses depend on locale (reference data resources)

### `users.language` column

`[EXAMPLE - Laravel migration]`

```php
$table->string('language', 5)->default('en');
```

- `NOT NULL`, default = configured fallback locale
- Validated against the supported-locales list on update
- Populated at user creation (invite flow copies inviter's locale or uses the configured default)

## What NOT to Do

- Do NOT hardcode user-facing strings in components, templates, or controller responses
- Do NOT install heavy i18n libraries (`react-i18next`, `i18next`, `FormatJS`, `lingui`, `next-intl`, etc.) when a lightweight solution suffices
- Do NOT cache the resolved locale in `localStorage`, `sessionStorage`, or cookies
- Do NOT autodetect locale for authenticated users - `user.language` always wins
- Do NOT create a separate `translations` table for reference data - use a JSON column
- Do NOT name the localized accessor the same as the underlying column (e.g. `getNameAttribute()` on a row with a `name` column) - it would shadow the column. Use an explicit `localized_name`-style accessor so callers opt in to localization.
- Do NOT read `Accept-Language` on authenticated backend requests
- Do NOT commit keys present in one locale but missing in another - parity is enforced in review
- Do NOT build translation keys dynamically from untrusted input (`t(\`errors.${code}\`)` is OK only when `code` is a whitelisted enum)
- Do NOT reload the page on language change

## Definition of Done (Reviewer Checklist)

For any task touching user-facing text, confirm before approval:

- [ ] No hardcoded user-facing strings in components, templates, controller responses
- [ ] All new keys exist in ALL supported locale bundles (frontend AND backend where applicable)
- [ ] Key naming follows dot-notation + camelCase, first segment matches namespace
- [ ] Placeholders follow each side's convention (`{name}` frontend, framework-native on backend)
- [ ] `t()` calls never receive a dynamically concatenated, unvalidated key
- [ ] New reference-data models expose a localized accessor, resources return plain strings
- [ ] No heavy i18n library added to package manifests without justification
- [ ] No `localStorage` / cookie writes for locale preference
- [ ] Authenticated requests resolve locale from `user.language`, not headers
- [ ] Language switch in Settings works without page reload, and reloads locale-dependent queries
- [ ] No hardcoded fallback locale strings - all use the framework config / frontend `DEFAULT_LOCALE` constant
- [ ] Reference models with `name_translations` also have a `name` VARCHAR column (default-locale cached copy), filled via seed
- [ ] Localized accessor is named `localized_name` (or equivalent), not `name`, to avoid shadowing the column
